# 0.9.37 review fixes

Status: record of package 0.9.37. Package 0.9.39 is current. The 0.9.36 note stays the record of opening-match continuation, the sole-survivor final assessment, match-sized evidence summaries, unreviewed relation rows, the withheld-list export, and raised-code variance. This note does not change `pattern_min_cases` (2), the axial token number (24000 per step), `batch_size` (1), or the 6000 request budgets. `auto_size_decision_calls` stays off. `selection_consolidation` stays off. Tier 4 stays human-only. Undefined metrics stay null. Human input still arrives through `interrupt()` and `Command(resume=...)`. No paid call is added. No LLM judge is added. No live evaluation was run.

A decision review that reports every item reviewed, including a count such as 355 of 355, establishes processing coverage. A passing synthetic fixture does the same. Neither establishes that a selection is valid. Human-adjudicated examples are not in this package.

## Decisions

Giving core selection its own allowance is a decision. In live run v42 the core bracket had 54 candidates in 6 opening matches of about 5.8k tokens each. Two matches were sent. The core step then hit the same 4-call, 24000-token default the other decision steps use. The stop was labeled `core_pair_exceeds_request_budget`, and the preflight recorded the shortfall without warning. `max_core_review_calls` and `max_core_review_tokens` bound only the core step. When they are omitted, that step keeps the existing defaults: 4 calls and 24000 tokens. Relation review, saturation review, and the coding pool stay where they are. The per-request limit stays 6000. The rule is `core_budget_rule` `separate_core_allowance_v1`.

Pricing the whole bracket before the first send is a decision. Unavoidable cost is every opening match, priced with no same-round prior. Contingent cost is every later round, assuming each match advances its first candidate and carrying a full 240-character prior for each earlier match. A `no_suitable_candidate` abstention advances nobody, so that later work does not happen. The preflight keeps those two figures separate and reports the calls and tokens available and any shortfall. The warning is recorded when an opening request is over the per-request cap or when the opening or contingent work exceeds the allowance. The rule is `core_preflight_rule` `opening_unavoidable_later_contingent_v1`.

Stopping before spending is a decision. If the remaining opening matches do not fit the call allowance, the token allowance, or the 6000 per-request cap, nothing is sent. The outcome stays `selection_unresolved`. `allow_partial_core_review` is off. Turning it on sends the opening matches that fit and persists the bracket as incomplete and resumable. A no-spend shortfall is also persisted, with `core_resume.resumable` true, so a larger allowance can start the same plan. The rule is `core_partial_execution_rule` `partial_core_off_by_default_v1`.

Naming the resource that actually ran out is a decision. `core_request_too_large` is a live payload over the 6000 cap. `core_call_allowance_insufficient` is the core call ceiling. `core_token_allowance_insufficient` is the core token ceiling. When more than one applies, the primary reason is the request cap, then the call allowance, then the token allowance, and every applicable reason stays on the review. A pair the planner cannot partition still stops as `core_pair_exceeds_request_budget` before a send. A one-candidate chunk of a larger set still stops as `core_bracket_incomplete`. Call or token exhaustion is no longer rewritten to either of those names. The rule is `core_stop_reason_rule` `request_call_or_token_v1`.

Opening matches quote rationales from earlier rounds only. Same-round rationales were what pushed a later opening payload over 6000 after the first matches had been sent, which is how v42's stop was mislabeled. Prior-round rationales still travel to later rounds.

Reusing a finished match is a decision. A validated select, and an abstention whose reason is `no_suitable_candidate`, is reused when its payload fingerprint and its policy fingerprint still match. `insufficient_evidence` and an incomplete match are not reused, and they are not rewound. A changed payload or a changed policy drops that match and every match after it. An export written before fingerprints existed, including a 0.9.36 export, is trusted once and then stamped from the frozen candidates. A later edit is detected. A changed partition starts a new plan instead of raising. Call and token ceilings are outside the plan hash and the policy fingerprint, so a larger allowance continues the same plan. Reused matches are not sent again. The calls already recorded for them still count against the ceiling. The rule is `core_match_reuse_rule` `reuse_validated_match_v1`.

Auto-sizing stays off. That is a decision. `auto_size_core_review` computes the opening plus contingent calls and tokens. `max_core_review_call_hard_limit` and `max_core_review_token_hard_limit` bound that result, and they apply only when auto-size is on. When those hard limits are omitted, the configured allowance is the ceiling, so turning auto-size on does not expand it. The preflight is a character heuristic for the payloads in this run. A low figure on this model is not a safe assumption for every provider. Focused `auto_size_decision_calls` is unchanged. The rule is `core_auto_size_rule` `bounded_core_auto_size_off_v1`.

## Frozen axial export

`load_axial_export(directory)` reads `selective_run.json` or `axial_run.json`, plus `core_candidates.json`. When candidate rows are present it sets `freeze_core_candidates`, and core selection uses those rows instead of scoring the codebook again.

`resume_core_selection(directory, model, decision_mode="llm", max_core_review_calls=..., max_core_review_tokens=...)` is `selective_code` on that loaded export. `selective_code` on the directory does the same when `core_candidates.json` is present together with `selective_run.json` or `axial_run.json`, and the directory is not also a focused export. A directory that still holds `focused_run.json` or `focused_selection.json` keeps the focused resume path, so an edited selection is honored. Focused coding and relation review are not run again. Pass a larger core allowance to spend it on matches that were not validated. `allow_partial_core_review` stays off unless the caller sets it.

The next eval can finish the 54-candidate v42 bracket from that export. The two stored `no_suitable_candidate` matches are trusted once, because a 0.9.36 export has no payload fingerprint, and then stamped. A larger core allowance sends the matches that remain.

## What this note does not change

`pattern_min_cases` stays 2. `max_axial_review_tokens` stays 24000 per step. `axial_token_budget` and `decision_token_budget` stay 6000. `batch_size` stays 1. `selection_consolidation` stays off. `auto_size_decision_calls` stays off. Tier 4 stays a human `verify`. No LLM judge is added. A metric that was not computed stays null. The 0.9.36 outcomes still hold: every opening match concluding `no_suitable_candidate` is `no_core_supported`; any required match left unreviewed or unresolved is `selection_unresolved`; a sole survivor still receives a final assessment; a completed final that supports a candidate is `core_selected`. Examining part of the eligible set means selection stopped early. It does not mean that no core exists.

The resume fingerprint stays `request_budget_v6`. The new procedure keys are part of that fingerprint, so a 0.9.36 checkpoint cannot resume.
